Zoom Chat
The ZoomMate bot in Zoom Team Chat — already shipped for the three base message types (New task detected, Completed, Need Clarification). This tab adds Workflow's states and shows what ships next. Slack and Microsoft Teams reuse this same set of cases, re-expressed in each platform's own card syntax — see the note below.
Why this reads differently from the email tab
Chat isn't static like email — the bot's buttons call back to a server, so Copy and jump-to-chat both actually work here, and a card can update itself in place after a click instead of going stale. That's why Copy, removed from the email tab, is back on every card below.
One hard constraint from the bot platforms: every actionable button must sit at the card's top level. There's no hidden menu, no nested layer, no nested "show more" behind which a button can live — show more/less may only hide text, never a button. Multiple recipients still split into separate messages, never one card with two blocks, same rule as email.

Enable IM notifications for My Notes P1
The parent category for every chat channel. Turning it off stops all three at once. For Slack and Teams this switch only expresses whether your account wants follow-up cards sent — the Zoom bot still checks its own install and authorization state before delivering.
Why here, and how it resolves
Admins already look for anything notification-shaped in this one section, and the checkboxes inherit the account → group → user lock model for free. Summary and follow-ups are separate checkboxes because accounts routinely want one without the other, but neither needs its own switch — they are both My Notes email.
Send only when the admin checkbox for that kind is on and the user’s client switch is on and (for chat apps) the bot is installed and authorized. Admin off leaves the client controls visible but grayed with a hover explanation, so users understand it’s a policy, not a bug. Which statuses a user receives is theirs alone — the account does not narrow that list.
Slack and Teams: who owns the switch
We own intent — whether follow-up cards should go to chat at all, and which statuses. Ecosystem owns permission and delivery: the org-level enable lives in the Zoom app's config page in Zoom Marketplace, each user authorizes once inside Slack or Teams using that client's own sign-in, and the bot service consumes our full-volume events and drops anything from an unauthorized user.
So My Notes must not show a Slack or Teams on/off switch — a switch we can't enforce would lie. Those rows show connection state plus a link into the app, and a user with no Slack account simply has no choice to make. Zoom Team Chat keeps a real switch because that bot is ours.
HITL mapping
Every JSON shape ZoomMate's human-in-the-loop tool can currently hand back, and the fixed email layout each one maps to. Reference for handoff — the part_id under each card is the source example it covers.
The mapping rule
Never parse or re-render spec.fields / spec.actions — that couples the email to a protocol we don't own. Take four stable pieces instead: spec.title → subject, spec.subtitle (or the first display field's text, if there's no subtitle, or nothing at all if neither exists) → body copy, a table or file_to_confirm field → a one-line count or filename mention (never the table or file picker itself), and one Review and continue button that deep-links into Zoom.
Three exceptions. An action of type: "link" is a plain URL — safe to expose as its own button, it behaves identically in email or in-app. A title or subtitle longer than a sentence gets truncated with an ellipsis — the spec has no length contract, our subject line does. And several specs sharing one meta.batch_id collapse into a single "N items need your review" card instead of N separate emails.
